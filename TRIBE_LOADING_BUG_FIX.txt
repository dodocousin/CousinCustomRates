# Tribe Member Count Lazy-Loading Bug - FIXED

## Git Commit: b330fce
## Branch: test
## Status: ✅ COMPLETE - Pushed to GitHub

---

## THE BUG

### Symptom:
TribeSizeMultiplier did not work until player opened tribe UI, even after waiting 60+ seconds.

### Root Cause:
ARK lazily loads tribe data on the client side. The old code used:
```cpp
playerState->MyTribeDataField().MembersPlayerDataIDSet_ServerField().Num()
```
This field is **EMPTY** until the player opens their tribe interface, causing:
- memberCount = 0
- TribeSizeMultiplier returns 1.0f (no effect)
- PostLogin hook was useless (data still not loaded)
- Timer refresh was useless (re-read empty data)

---

## THE FIX

### Solution: Server-Side Authoritative Data Loading
Use `AShooterGameMode::GetOrLoadTribeData()` which:
- Loads tribe data directly from save file/database
- Bypasses client-side lazy loading
- Excludes heavy tribe log data for performance
- Works immediately on player login

### Code Changes:

**File: Source/TargetedRates.h**

1. **Added Includes (lines 8-9):**
```cpp
#include <API/ARK/Ark.h>
#include <API/ARK/GameMode.h>
```

2. **Rewrote GetAndCacheTribeMemberCount() (lines 127-190):**

**Key Changes:**
- Uses `gameMode->GetOrLoadTribeData()` instead of `MyTribeDataField()`
- Uses `ETribeDataExclude::TribeLogAndTrackingPoints` for performance
- Handles solo players: `IsInTribe()` returns false → count = 1
- Better logging with teamId and member count
- More robust error handling

## TECHNICAL DETAILS

### API Used:
```cpp
bool AShooterGameMode::GetOrLoadTribeData(
    int tribeId,
    FTribeData* outTribeData,
    ETribeDataExclude excludeFlags
)
```

### Enum Values:
```cpp
enum class ETribeDataExclude : int {
    TribeNone = 0x0,
    TribeLog = 0x1,
    TrackingPoints = 0x2,
    TribeLogAndTrackingPoints = 0x3
};
```

### Performance:
- Tribe logs can be MB+ of text data
- Excluding them makes load microseconds instead of milliseconds
- Safe to call on every login
